# Atlas (versioned migrations)

## Layout and naming

- Default directory `migrations/` (`--dir file://migrations`, or `migration { dir = ... }` in an `atlas.hcl` env). Files are `YYYYMMDDHHMMSS_name.sql` (template `{{ now }}_{{ name }}.sql`); the version is the text before the first `_` and Atlas compares versions as strings, so keep 14 digits.
- `atlas.sum` sits next to the files: first line `h1:<dir sum>`, then one `<file> h1:<hash>` line per migration. Hashes are SHA-256, chained: each file's hash covers every earlier file name and content plus its own, and the directory sum hashes the list. Any byte changed in any file invalidates the sum.
- `--dir-format` (`atlas`, `golang-migrate`, `goose`, `flyway`, `liquibase`, `dbmate`) lets Atlas manage another tool's directory. When `stack.json` reports a non-`atlas` format, write the files per that tool's reference and come back here only for `atlas.sum` and the revisions table.
- In-file directives: `-- atlas:txmode none` (first line, no transaction), `-- atlas:delimiter \n\n` (statement separator for bodies with semicolons), `-- atlas:nolint`, `-- atlas:sum ignore`.

## Replay order

By version string, ascending. `atlas migrate apply` computes pending files from the revisions table: every file newer than the last revision is pending; a file older than the last revision with no revision row is "out of order" and fails under the default `--exec-order linear` (`linear-skip` ignores it, `non-linear` applies it). Transcribe in file order. Kept files keep their versions, so the history's order holds; new files (`deferred_foreign_keys`, `seed_reference_data`, `functions_and_triggers`, moved views) are numbered after `source.last_version` (`20231120100000` → `20231120100001_deferred_foreign_keys.sql`). A table split out of a multi-table original takes the next free second after it, which is **older** than the last revision of every existing database: see the baseline below.

## Reading originals into ops

Atlas files are plain SQL in the target dialect, often generated by `atlas migrate diff` with a comment per statement:

- `-- Create "users" table` + `CREATE TABLE "users" (...)` -> `create_table` with every column, inline `PRIMARY KEY`, `CONSTRAINT ... FOREIGN KEY ... ON DELETE`, `CHECK` and `UNIQUE` clauses recorded in their own lists
- `-- Modify "posts" table` + `ALTER TABLE "posts" ADD COLUMN "slug" character varying(80) NOT NULL, ADD CONSTRAINT "posts_user_id_fkey" FOREIGN KEY ...` -> one `add_column` and one `add_foreign_key` per clause of the same statement
- `-- Create index "posts_slug_key" to table: "posts"` + `CREATE UNIQUE INDEX ...` -> Index `{ "unique": true }`
- `-- Create enum type "status"` + `CREATE TYPE "status" AS ENUM (...)` -> `create_type`; later `ALTER TYPE "status" ADD VALUE 'archived'` -> `alter_type`
- Checkpoint files (`-- atlas:checkpoint`) already contain the whole schema at that point; transcribe only the files after the last checkpoint, and treat the checkpoint as a `create_table` per table (it is the consolidation Atlas did itself)
- Hand-written `-- atlas:txmode none` files: keep a note so the consolidated file for that table carries the directive

## Writing a consolidated table migration

Atlas's own generator quotes every identifier and writes one comment per statement; follow that style so later `atlas migrate diff` output stays consistent.

`migrations/20230110100000_create_invoices.sql` (the original's name, final content):

```sql
-- 20230110100000_create_invoices.sql: consolidated by consolidate-migrations on 2025-10-29.
-- Final definition of "billing"."invoices". Folded in: 20230305100100_add_invoice_status.sql,
--   20230801120000_invoice_customer_fk.sql, 20231120100000_invoice_indexes.sql
-- Create "invoices" table
CREATE TABLE "billing"."invoices" (
  "id" bigint NOT NULL GENERATED BY DEFAULT AS IDENTITY,
  "customer_id" bigint NOT NULL,
  "number" character varying(32) NOT NULL,
  "status" "billing"."invoice_status" NOT NULL DEFAULT 'draft',
  "amount_cents" bigint NOT NULL DEFAULT 0,
  "notes" text NULL,
  "issued_on" date NULL,
  "created_at" timestamptz NOT NULL DEFAULT now(),
  PRIMARY KEY ("id"),
  CONSTRAINT "invoices_number_key" UNIQUE ("number"),
  CONSTRAINT "invoices_amount_nonnegative" CHECK ("amount_cents" >= 0),
  CONSTRAINT "invoices_customer_id_fkey" FOREIGN KEY ("customer_id")
    REFERENCES "billing"."customers" ("id") ON UPDATE NO ACTION ON DELETE CASCADE
);
-- Create index "invoices_customer_id_status_idx" to table: "invoices"
CREATE INDEX "invoices_customer_id_status_idx" ON "billing"."invoices" ("customer_id", "status");
-- Set comment to table: "invoices"
COMMENT ON TABLE "billing"."invoices" IS 'One row per issued invoice';
```

A renamed table keeps the file of the original that created it (`…_create_bills.sql` now creates `"invoices"`); the header says `Renamed from "bills"`. An original that created several tables holds each final `CREATE TABLE` in plan order, unless the user chose to split it.

There is no down section: Atlas versioned migrations are forward-only (`atlas migrate down` is a Pro feature that computes the reverse itself). Do not write `-- Down` blocks.

## Writing a view migration

In `20230601090000_customer_summary.sql`, the original that created the view, when everything the final definition reads exists by then (else the plan moves it to the file of the final definition, or to a new file after the last original):

```sql
-- 20230601090000_customer_summary.sql: consolidated by consolidate-migrations on 2025-10-29.
-- Final definition of view "customer_summary". Folded in: 20230915110000_fix_customer_summary.sql
-- Create view "customer_summary"
CREATE VIEW "customer_summary" AS
SELECT c.id, c.name, count(i.id) AS invoice_count
FROM "billing"."customers" c
LEFT JOIN "billing"."invoices" i ON i.customer_id = c.id
GROUP BY c.id, c.name;
```

Plain SQL; no escape hatch needed.

## The extra files

New files only for what no kept file can hold, numbered after the last original.

- Prerequisites have no file of their own: `CREATE SCHEMA "billing"; CREATE EXTENSION IF NOT EXISTS "citext"; CREATE TYPE "billing"."invoice_status" AS ENUM ('draft', 'sent', 'paid');` go first in the kept file that created them, or in the earlier kept file the plan pulled them into (`moved_in`).
- Functions and triggers: at the end of their kept file, after its tables. Any file holding function bodies with semicolons starts with `-- atlas:delimiter \n\n` (or `-- atlas:delimiter ;;`) so each body is one statement (the delimiter then applies to every statement of that file, tables included); triggers after their functions. `functions_and_triggers` only for those reading something created after every candidate original.
- `deferred_foreign_keys`: `-- Modify "a" table` + `ALTER TABLE "a" ADD CONSTRAINT "a_b_id_fkey" FOREIGN KEY ("b_id") REFERENCES "b" ("id");` per FK whose target table's file comes later (and per cycle edge broken inside one file).
- `seed_reference_data`: the kept `INSERT` statements verbatim; add `-- atlas:nolint` only if the project's lint rules complain about data changes.

## Schema snapshot to cross-check

When the project uses the declarative flow (`atlas migrate diff --to file://schema.hcl` or `schema.sql`, the `src` of an `atlas.hcl` env), that file is the source of truth. Compare manifest tables with the HCL blocks without a database: one `table "invoices"` block per manifest table, a `column "x" { type = ...; null = ...; default = ... }` per Column, `primary_key { columns = [column.id] }`, `index "name" { unique = true; columns = [...] }`, `foreign_key "name" { columns, ref_columns, on_delete }`, `check "name" { expr = ... }`. A `schema.sql` is compared the same way as the consolidated `CREATE TABLE` statements. Note in the report any column present in the manifest but absent from the schema file (the schema file was edited by hand without a diff).

Built-in alternative: with a dev database available, `atlas migrate diff consolidated --dir file://migrations_new --to file://schema.hcl --dev-url "docker://postgres/16/dev"` makes Atlas emit the whole schema as one file. It is one new file for everything instead of the originals' files, and the skill does not run databases, but offer it when the project has a `schema.hcl` and the user only wants a flat baseline.

## After placing the files

- Run `atlas migrate hash --dir file://migrations` after placing the files and after every later edit: kept files changed content and removed files are gone, so without it every command fails with `checksum mismatch`. Commit `atlas.sum` with the files.
- Keep the archive outside the migration directory; any `.sql` there is a migration and enters the sum, and every archived original that created a table has the same version as its kept file.
- `atlas migrate validate --dir file://migrations` checks the sum; adding `--dev-url` also replays the files on an empty dev database (needs Docker or a scratch DB).
- `atlas migrate lint --latest N --dev-url ...` on the new files flags destructive and non-linear changes; expect "non-linear" warnings in CI if the lint job compares against a branch that still has the old files, or when split files sit between existing versions.
- Checkpoints (`atlas migrate checkpoint`, Pro) are Atlas's own consolidation; if the project already uses them, prefer that mechanism over this skill.

## Tracking table and reconciliation

Table `atlas_schema_revisions` (schema `atlas_schema_revisions` when the URL is not bound to one schema, else the connected schema; `--revisions-schema` overrides). Columns: `version` (PK, text), `description`, `type` (bitmask: 1 baseline, 2 execute, 4 resolved), `applied`, `total` (statement counts), `executed_at`, `execution_time`, `error`, `error_stmt`, `hash` (the file's `atlas.sum` hash), `partial_hashes`, `operator_version`.

- Row without a file: ignored, unless it is the last revision and partially applied (`applied != total`), which fails with a missing-migration error.
- File without a row: pending if newer than the last revision; otherwise a non-linear error under the default exec order.
- Modified file: detected through `atlas.sum`, not the `hash` column; `atlas migrate status` reports hash drift.

Precheck (`precheck.sh`), before the swap, with the old directory: `atlas migrate status --url "$DATABASE_URL"` must report `Already at latest version`. A database that is behind would see the kept versions as applied and miss their folded changes.

Baseline an existing database with the tool's own command, never with hand-written inserts (the `hash` column must match `atlas.sum`):

```sh
atlas migrate hash --dir file://migrations
atlas migrate set 20231120100002 --dir file://migrations --url "$DATABASE_URL"   # version of the last file in the plan
atlas migrate status --dir file://migrations --url "$DATABASE_URL"
```

`migrate set <version>` deletes revisions newer than `<version>`, marks a partial revision at `<version>` as resolved, and writes a `type = resolved` revision with the right hash for every file after the last revision up to `<version>`, so the new files after the last original are covered. Rows of removed originals stay and are harmless; kept files keep their rows. Two things to verify on a copy or staging before the next deploy, both unverified:

- The kept revisions still carry the hash of the original content (and the `atlas.sum` hashes are chained, so every kept file's sum line changed). Check that `atlas migrate status` / `migrate apply` report no hash drift or history change for them.
- Split files placed between originals are older than the last revision. Check that `migrate set` recorded them; if `status` lists them as pending, `apply` fails on them under the default linear exec order.

A fresh database runs `atlas migrate apply`; an unmanaged database with the schema already in place takes `atlas migrate apply --baseline <version of the last file>`.

## Quirks

- `atlas migrate set` with no version argument on a database that has revisions syncs to the last file; with an empty directory it purges the revisions table.
- `atlas migrate apply` on a non-empty database with no revisions refuses unless `--baseline` or `--allow-dirty` is given.
- Every file runs in its own transaction by default; `CREATE INDEX CONCURRENTLY` and some `ALTER TYPE` forms need `-- atlas:txmode none` as the first line.
- Partial failure on MySQL (no transactional DDL) leaves a revision with `applied < total`; Atlas resumes from the failed statement on the next apply.
- `atlas.sum` hashes file names too: renaming a file is a change.
- Atlas also reads other directory formats; `format = goose` in `atlas.hcl` means the files carry goose annotations even though the sum and revisions are Atlas's.
- Many lint analyzers and `migrate down`, `migrate checkpoint`, `migrate rebase` are Atlas Pro features; the open-source CLI still does hash, set, apply, status and validate.
