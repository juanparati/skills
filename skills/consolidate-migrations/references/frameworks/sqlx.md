# SQLx (0.8)

## Layout and naming

- `migrations/` at the crate root by default (`sqlx migrate --source <dir>`, `[migrate] migrations-dir` in `sqlx.toml`, or the path argument of `sqlx::migrate!("db/migrations")`).
- Files are `<VERSION>_<description>.sql` (simple) or a pair `<VERSION>_<description>.up.sql` + `.down.sql` (reversible). `VERSION` is any positive `i64`: `sqlx migrate add` writes a UTC timestamp `YYYYMMDDHHMMSS` or, with `--sequential` (`-s`) or when the last two versions differ by 1, the next integer. Sorting is numeric. The description stored in the tracking table is the file name part with `_` replaced by spaces.
- `sqlx migrate add -r <name>` (`--reversible`) creates the pair; without a flag it copies the style of the latest existing migration. Simple and reversible files may coexist.
- Files not ending in `.sql` are ignored; a `.sql` file whose name has no integer prefix is an error (configurable via `unrecognized-sql-files` in `sqlx.toml`).
- `-- no-transaction` as the very first line runs that file outside a transaction.
- Kept files keep their exact name, so version **and** description (both come from the name) and style (simple `.sql`, or reversible `.up.sql` + `.down.sql`) stay the original's; only the content changes. New files (`deferred_foreign_keys`, `seed_reference_data`, `functions_and_triggers`, moved views, split-out tables) are numbered after the last original (a split-out table: the next free second after its original, when that still sorts before the next one). The plan names new files simple `.sql`; in a reversible project pass `--ext up.sql` to `plan_order.py` and write the `.down.sql` beside each.

## Replay order

Numeric by version. `sqlx migrate run` (and `Migrator::run`) first checks every applied row has a file and a matching checksum, then applies files with no row in ascending order, whatever their position relative to applied ones (a lower, unapplied version is simply run). Transcribe in numeric order. The consolidated set keeps that order: kept files sit at their original versions, new ones come after.

## Reading originals into ops

Plain SQL. Transcribe `.sql` / `.up.sql`; use `.down.sql` only to confirm. Idioms:

- `id BIGSERIAL PRIMARY KEY` / `id BIGINT GENERATED ALWAYS AS IDENTITY PRIMARY KEY` -> Column `{ "type": "bigserial" | "bigint", "primary": true, "auto_increment": true }`
- `user_id UUID NOT NULL REFERENCES users(id) ON DELETE CASCADE` -> Column + ForeignKey `{ "name": null, "columns": ["user_id"], "ref_table": "users", "ref_columns": ["id"], "on_delete": "cascade" }`
- `CREATE TABLE IF NOT EXISTS` -> `create_table` (the guard has no schema meaning)
- `ALTER TABLE t ALTER COLUMN c TYPE text, ALTER COLUMN c SET NOT NULL` -> one `alter_column` with `{ "type": "text", "nullable": false }`
- A trigger function in `$$ ... $$` -> `create_function`; SQLx sends the whole file as one batch, so nothing needs splitting
- `-- no-transaction` + `CREATE INDEX CONCURRENTLY` -> Index with a note `"concurrently"` so the consolidated file keeps the directive

## Writing a consolidated table migration

`migrations/20230110100000_create_invoices.up.sql`, the kept file that created the table (a simple `20230110100000_create_invoices.sql` stays simple):

```sql
-- Consolidated: final billing.invoices (created here); folded:
--   20230305100100_add_invoice_status.up.sql, 20230801120000_invoice_customer_fk.up.sql,
--   20231120100000_invoice_indexes.up.sql
CREATE TABLE billing.invoices (
    id            BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    customer_id   BIGINT NOT NULL,
    number        VARCHAR(32) NOT NULL,
    status        billing.invoice_status NOT NULL DEFAULT 'draft',
    amount_cents  BIGINT NOT NULL DEFAULT 0,
    notes         TEXT,
    issued_on     DATE,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    updated_at    TIMESTAMPTZ NOT NULL DEFAULT now(),
    CONSTRAINT invoices_number_key UNIQUE (number),
    CONSTRAINT invoices_amount_nonnegative CHECK (amount_cents >= 0),
    CONSTRAINT invoices_customer_id_fkey FOREIGN KEY (customer_id)
        REFERENCES billing.customers (id) ON DELETE CASCADE
);
CREATE INDEX invoices_customer_id_status_idx ON billing.invoices (customer_id, status);
COMMENT ON TABLE billing.invoices IS 'One row per issued invoice';
COMMENT ON COLUMN billing.invoices.amount_cents IS 'Total in minor units';
```

`20230110100000_create_invoices.down.sql` (rewritten too, though it is never hashed):

```sql
DROP TABLE billing.invoices;
```

The schema, the `invoice_status` type and `billing.customers` come from earlier kept files; a type created by a later original moves into this file when this table is the earliest that needs it, and an FK to a table created later goes to `deferred_foreign_keys`. A renamed table keeps the file of the original that created it (`..._create_bills.up.sql` now creating `invoices`): name the former table in the header. Keep the `-- no-transaction` line first in any file that needs it; a comment above it defeats the detection, so the header goes below it.

## Writing a view migration

`20230601090000_customer_summary.up.sql`, the kept file that created the view (a new `<version>_create_customer_summary_view.sql` after the last original only when even the original holding its final definition comes too early):

```sql
-- Consolidated: final view customer_summary (created here); folded: 20230915110000_fix_customer_summary.up.sql
CREATE VIEW customer_summary AS
SELECT c.id, c.name, count(i.id) AS invoice_count
FROM billing.customers c LEFT JOIN billing.invoices i ON i.customer_id = c.id
GROUP BY c.id, c.name;
```

Down: `DROP VIEW customer_summary;`. SQL throughout; no escape hatch.

## The extra files

New files, after the last original, only when the plan lists them:

- `functions_and_triggers`: functions then triggers in one file, only those no original can hold (they read something created after every candidate); `$$` bodies are fine.
- `deferred_foreign_keys`: `ALTER TABLE a ADD CONSTRAINT a_b_id_fkey FOREIGN KEY (b_id) REFERENCES b (id);` per deferred FK (target created in a later file, or a cycle edge); down drops it.
- `seed_reference_data`: the kept `INSERT` statements verbatim.

Prerequisites have no file of their own: `CREATE SCHEMA billing; CREATE EXTENSION IF NOT EXISTS citext; CREATE TYPE billing.invoice_status AS ENUM ('draft', 'sent', 'paid');` stay in the file that created them, or move into an earlier kept file that needs them (if `sqlx.toml` lists `create-schemas`, SQLx creates those schemas itself before migrating; skip the `CREATE SCHEMA` for them).

## Schema snapshot to cross-check

None. `.sqlx/query-*.json` (from `cargo sqlx prepare`) describes each compile-time-checked query, including `describe.columns[].type_info` and `nullable`; spot-check a few against the manifest's column types, but it is not a schema. `sqlx migrate info` needs a database.

## After placing the files

- `sqlx::migrate!()` embeds the directory at compile time, so rebuild. The compiler only notices changes when `build.rs` prints `cargo:rerun-if-changed=migrations` (`sqlx migrate build-script` writes that file); otherwise touch the source that calls the macro.
- The `.sqlx/` offline data is keyed by query text, not by migrations; it stays valid. If the consolidated schema changed a column type by mistake, `cargo sqlx prepare --check` against a freshly migrated database is what catches it.
- Keep the archive outside `migrations/`: every `.sql` there is parsed, a file without an integer prefix aborts resolution, and the archived originals carry the same versions as the kept files.
- `sqlx migrate info` against any database lists `installed`, `pending` or `installed (different checksum)` per file; after the baseline every file must be `installed`.

## Tracking table and reconciliation

Table `_sqlx_migrations` (override with `[migrate] table-name`): `version BIGINT PRIMARY KEY`, `description TEXT`, `installed_on TIMESTAMPTZ DEFAULT now()` (TIMESTAMP on MySQL/SQLite), `success BOOLEAN`, `checksum BYTEA` (BLOB on MySQL/SQLite), `execution_time BIGINT` (nanoseconds; `-1` while a migration is in flight).

Checksum: SHA-384 of the full text of the applied file (`.sql` or `.up.sql`; `.down.sql` is never hashed or recorded), as read from disk, so line endings count. With `[migrate] ignored-chars` in `sqlx.toml` the listed characters are stripped before hashing.

- Row without a file: `migrate run`, `revert` and `Migrator::run` fail with `migration N was previously applied but is missing in the resolved migrations` unless `--ignore-missing` (`Migrator::set_ignore_missing(true)`).
- Row with a different checksum: `migration N was previously applied but has been modified`; no flag overrides it.
- Row with `success = false`: `migration N is partially applied; fix and remove row`.
- File without a row: pending, applied on the next run.

So all three cases need SQL: removed originals lose their rows, every kept version gets the checksum of its new content, new files get a row with theirs. `baseline.py --dir migrations` (after the files are final: it hashes the bytes of each `.sql` / `.up.sql`, header comment included) writes `precheck.sql` and `baseline.sql`:

```sql
-- precheck.sql: must return no rows (any row = that database has not run every original; migrate it on the old history first)
SELECT m.v AS not_applied FROM (SELECT 20230110100000 AS v UNION ALL SELECT 20230305100100 AS v UNION ALL ...) m
WHERE NOT EXISTS (SELECT 1 FROM _sqlx_migrations t WHERE t.version = m.v AND t.success = TRUE);
```
```sql
-- baseline.sql (Postgres)
DELETE FROM _sqlx_migrations WHERE version IN (20230305100100, 20230801120000, 20231120100000);  -- removed originals
UPDATE _sqlx_migrations SET checksum = decode('<96 hex chars>', 'hex') WHERE version = 20230110100000;  -- one per kept file
INSERT INTO _sqlx_migrations (version, description, success, checksum, execution_time)
VALUES (20231120100001, 'deferred foreign keys', true, decode('<96 hex chars>', 'hex'), 0);  -- one per new file
-- MySQL: UNHEX('<hex>')    SQLite: X'<hex>'
```

The `DELETE` is required unless every deploy passes `--ignore-missing`; the `UPDATE` has no alternative (a checksum mismatch is fatal, no flag). Kept rows keep their `description` and `installed_on`. To regenerate a hash by hand: `python3 -c 'import hashlib,sys;print(hashlib.sha384(open(sys.argv[1],"rb").read()).hexdigest())' migrations/<file>`. The library has a `Migrator::skip` / `conn.skip()` path that inserts rows without executing, but the CLI does not expose it (unverified).

## Quirks

- The checksum covers the header comment too: editing the "Consolidated" comment after baselining breaks the hash, on every existing database. Baseline last, from the final files.
- A database that ran `20230110100000_create_invoices` but not yet `20230305100100_add_invoice_status` sees the rewritten file as applied (once its checksum is updated) and never gets `status`; nothing fails. The precheck catches it.
- Reversible and simple files sort together by version; `revert` only works on versions that have a `.down.sql`.
- `sqlx migrate add` infers sequential numbering from the last two files. Kept files keep the originals' versions, but the new files come last and `plan_order.py` numbers them one apart (`...100001`, `...100002`), so with two or more new files the next `add` continues sequentially. Pass `--timestamp` once, or set `[migrate] defaults.migration-versioning = "timestamp"` in `sqlx.toml`.
- Each file runs in one transaction unless `-- no-transaction`; on MySQL DDL auto-commits and a failure leaves a `success = false` row that blocks further runs until deleted.
- `migrate run --target-version` cannot go below the latest applied version; `revert --target-version 0` reverts everything.
- SQLx takes an advisory lock (Postgres/MySQL) while migrating; a hung baseline session blocks deploys.
