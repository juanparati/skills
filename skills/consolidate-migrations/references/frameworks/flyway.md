# Flyway (10 / 11)

## Layout and naming

- Default location `classpath:db/migration` (Spring Boot `spring.flyway.locations`; CLI `locations=filesystem:sql` in `flyway.toml`/`flyway.conf`). Several locations are merged.
- Versioned: `V<version>__<description>.sql` (prefix `V`, separator `__`, suffix `.sql`; all configurable, `sqlMigrationPrefix`, `sqlMigrationSeparator`, `sqlMigrationSuffixes`). Version is dotted or underscore-separated digits: `V1__`, `V2_1__`, `V1.2.3__`, `V20240601120000__`. Description words separated by `_`, shown with spaces in the history table.
- Repeatable: `R__<description>.sql`, no version. Undo: `U<version>__` (Teams). Baseline migration: `B<version>__`, a cumulative script new environments start from instead of older versions; Flyway's own squash, which this skill does not use because it leaves the history files in place.
- Java migrations (`V1__Name.java` implementing `JavaMigration`) exist; the skill handles only SQL files and reports Java ones as unresolved.
- Consolidated files: a kept original keeps its name (`V3__create_orders.sql` now holds the final orders table); originals that only altered or dropped things disappear. New files continue the project's numbering style after the highest existing version: integers -> `V15__deferred_foreign_keys.sql`; timestamps -> `V20240601120001__deferred_foreign_keys.sql`. A table split out of a multi-table original gets a dotted version right after it, `V3.1__create_order_items.sql`, which sorts between `V3` and `V4`.

## Replay order

By version, numerically: underscores become dots, each dot-separated part is compared as an integer (`V1_2` == `V1.2`, `V10` > `V9`, `V1.2` == `V1.2.0`). Repeatables run after all pending versioned migrations, alphabetically by description, and again whenever their checksum changes. A versioned migration with a version lower than the highest applied one is **ignored** unless `outOfOrder=true` (default false). So transcribe originals sorted by that numeric rule, not by file name, and number new files above the current maximum. A dotted split version (`V3.1`) is below it on purpose: existing databases get its row from the baseline, fresh ones run it in order.

## Reading originals into ops

Plain SQL per dialect, so reading is SQL parsing. What to watch:

- `CREATE TABLE users (id BIGSERIAL PRIMARY KEY, email TEXT NOT NULL UNIQUE)` -> `create_table`; `BIGSERIAL` is `type: "bigint"`, `auto_increment: true` and an implicit sequence `users_id_seq` (do not add a `create_sequence` op, the type recreates it); the inline `UNIQUE` is `unique: true` on the column (Postgres names it `users_email_key`).
- `ALTER TABLE orders ADD COLUMN status TEXT NOT NULL DEFAULT 'draft'` -> `add_column`. `ALTER TABLE orders ALTER COLUMN status DROP DEFAULT` -> `alter_column` with `"default": null, "clear_default": true`.
- `CREATE INDEX CONCURRENTLY ix ON orders (user_id) WHERE status = 'paid'` -> a normal `add_index` with `where` as written; drop `CONCURRENTLY`. It forced the original file to carry `-- flyway:executeInTransaction=false`; the consolidated create-table file does not need that, the table is empty.
- `CREATE OR REPLACE VIEW v AS SELECT ...` -> `create_view`; a later `CREATE OR REPLACE` of the same name is also `create_view` (replay keeps the last).
- Placeholders `${schema}` / `${flyway:defaultSchema}` are substituted at run time; keep them verbatim in `raw`, `default` and `definition` and reuse them in the consolidated files.
- `R__` files hold views, functions and grants that were re-run on change; transcribe their final content as `create_view` / `create_function` ops, and keep the repeatable files themselves (see Quirks).

## Writing a consolidated table migration

`V3__create_orders.sql`, the kept original (Postgres):

```sql
-- Consolidated by consolidate-migrations: final definition of orders.
-- Folded: V3__create_orders.sql (this file), V7__add_order_status.sql,
-- V9__order_total_check.sql, V14__order_notes.sql

CREATE TABLE orders (
    id          BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
    user_id     BIGINT        NOT NULL,
    number      VARCHAR(32)   NOT NULL,
    status      VARCHAR(16)   NOT NULL DEFAULT 'draft',
    total       NUMERIC(12,2) NOT NULL DEFAULT 0,
    notes       TEXT,
    created_at  TIMESTAMPTZ   NOT NULL DEFAULT now(),
    CONSTRAINT orders_number_key UNIQUE (number),
    CONSTRAINT orders_total_check CHECK (total >= 0),
    CONSTRAINT orders_user_id_fkey FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE
);

CREATE INDEX orders_user_id_status_idx ON orders (user_id, status);

COMMENT ON TABLE orders IS 'Customer orders';
COMMENT ON COLUMN orders.status IS 'draft | paid | cancelled';
```

Flyway has no `down`. If the project uses undo migrations (Teams), undo files follow the kept versions: `U3__create_orders.sql` with `DROP TABLE orders;`, new `U` files for new versions, and the `U` files of removed originals archived with them; otherwise none. A kept multi-table original (the user chose not to split) holds every table it created, in FK order. Flyway runs each file in its own transaction on databases with transactional DDL.

## Writing a view migration

No escape hatch needed, it is already SQL: `CREATE VIEW customer_summary AS SELECT ...;` in its creating file when everything it reads exists by then, otherwise in a new file after the last original, `V16__create_customer_summary_view.sql`. If the project kept views in repeatables (`R__views.sql`), keep that convention instead: one `R__view_customer_summary.sql` with `CREATE OR REPLACE VIEW ...` (or `DROP VIEW IF EXISTS ...; CREATE VIEW ...` on MySQL/MSSQL), and do not also create the view in a `V` file. Repeatables must be re-runnable, so `OR REPLACE` / `IF EXISTS` is mandatory there.

## The extra files

New files, in plan order after the last original (`V14` here, every kind present):

- `functions_and_triggers`: `V15__functions_and_triggers.sql`, only what could not stay in its creating file; `$$`-quoted bodies are fine, Flyway's parser understands dollar quoting (MySQL `DELIMITER` is not needed, Flyway splits statements itself). For MSSQL `CREATE PROCEDURE` must be the first statement of a batch: separate with `GO`.
- moved views: `V16__create_customer_summary_view.sql`.
- `deferred_foreign_keys`: `V17__deferred_foreign_keys.sql` with `ALTER TABLE users ADD CONSTRAINT users_current_team_id_fkey FOREIGN KEY (current_team_id) REFERENCES teams (id) ON DELETE SET NULL;`.
- `seed_reference_data`: `V18__seed_reference_data.sql` with `INSERT INTO countries (id, name) VALUES (1, 'US'), (2, 'CA');` (`ON CONFLICT DO NOTHING` if the originals were idempotent).

Prerequisites get no file: `CREATE EXTENSION IF NOT EXISTS citext; CREATE SCHEMA IF NOT EXISTS billing; CREATE TYPE invoice_status AS ENUM ('draft','paid'); CREATE SEQUENCE invoice_numbers START 1000;` stay in the kept original that created them, or move to the top of an earlier kept file that needs them. `CREATE EXTENSION` / `CREATE TYPE` are transactional on Postgres, no flag needed.

## Schema snapshot to cross-check

None. Flyway is SQL-only; there is no model. Spring Boot projects with JPA entities can be cross-checked the same way as Doctrine mappings (`@Table`, `@Column(nullable, length)`, `@JoinColumn`, `@ManyToMany` implicit join tables), but entities often lag behind the schema, so treat a mismatch as a note, not an error. `spring.jpa.hibernate.ddl-auto=validate` is the user's runtime check.

## After placing the files

- Move originals outside every configured location (e.g. `src/main/resources/db/archive/` is fine, `db/migration/archive/` is not: `locations` are scanned recursively). A kept file and its archived original share a version, so an archive still scanned fails at once (`Found more than one migration with version 3`).
- Nothing to regenerate. Java projects: rebuild the jar, migrations are classpath resources.
- Checksums change for every kept `V` file: `validate` (run by `migrate`) fails on existing databases until the baseline's `flyway repair`. Checksums also change for repeatables you rewrote; that is expected, they re-run on the next `migrate` (a view `CREATE OR REPLACE` is harmless).

## Tracking table and reconciliation

- Table `flyway_schema_history` (setting `table`, Spring `spring.flyway.table`), one row per applied migration: `installed_rank INT PRIMARY KEY`, `version VARCHAR(50) NULL` (null for repeatables), `description VARCHAR(200)`, `type VARCHAR(20)` (`SQL`, `JDBC`, `BASELINE`, `DELETE`, `UNDO_SQL`...), `script VARCHAR(1000)` (file name), `checksum INT NULL`, `installed_by VARCHAR(100)`, `installed_on TIMESTAMP DEFAULT now`, `execution_time INT`, `success BOOLEAN`.
- Checksum: CRC32 over the migration file read line by line, each line's UTF-8 bytes fed to the CRC without the line terminator, BOM stripped from the first line. So line endings and encoding do not matter, but any other byte does; placeholders are hashed unreplaced (unverified).
- Applied row whose file is gone: **strict at validate time**. `migrate` runs `validate` first (`validateOnMigrate=true`) and fails with "Detected applied migration not resolved locally" unless `ignoreMigrationPatterns` contains `*:missing` (default is `*:future` only). A file without a row runs if its version is above the current maximum; below it, it is ignored (`outOfOrder=false`) and validate reports it as ignored.
- Baseline for an existing database, in the order `baseline.py` emits it (`precheck.sql` first, it must return no rows: originals that database has not run successfully):

```sql
-- precheck.sql
SELECT m.v AS not_applied FROM (SELECT 'V1__create_users.sql' AS v UNION ALL ... UNION ALL SELECT 'V14__order_notes.sql' AS v) m
WHERE NOT EXISTS (SELECT 1 FROM flyway_schema_history t WHERE t.script = m.v AND t.success = TRUE);
-- baseline.sql
-- 1. forget the removed originals; kept files keep their rows
--    (or run `flyway repair` after moving them: it marks them type DELETE instead)
DELETE FROM flyway_schema_history WHERE script IN ('V7__add_order_status.sql', 'V9__order_total_check.sql', 'V14__order_notes.sql');
-- 2. record the new files as applied; checksum left NULL on purpose, step 3 fills it
INSERT INTO flyway_schema_history (installed_rank, version, description, type, script, checksum, installed_by, installed_on, execution_time, success)
VALUES ((SELECT COALESCE(MAX(h.installed_rank), 0) + 1 FROM flyway_schema_history h), '17', 'deferred foreign keys', 'SQL',
        'V17__deferred_foreign_keys.sql', NULL, 'consolidate', CURRENT_TIMESTAMP, 0, TRUE);
-- 3. realign every checksum (kept files changed content, new rows are NULL)
-- flyway repair
```

MySQL: the self-referencing subquery needs a derived table, `(SELECT COALESCE(MAX(r), 0) + 1 FROM (SELECT MAX(installed_rank) r FROM flyway_schema_history) x)`. `repair` realigns checksums, descriptions and types of applied rows with the files on disk, removes failed rows and marks rows without a file as `DELETE`; it needs the same `locations` as `migrate`. The tool's own alternative when the table can be emptied (after the same precheck): `DELETE FROM flyway_schema_history;` then `flyway baseline -baselineVersion=18` (the highest version; defaults: `baselineVersion=1`, `baselineDescription="<< Flyway Baseline >>"`), which inserts one `BASELINE` row and makes every version `<= 18` count as applied; `baselineOnMigrate=true` does that automatically on a non-empty schema that has no history table.

## Quirks

- New files numbered below the current maximum are silently skipped (`outOfOrder=false`); number them above it. The one exception is a dotted split version (`V3.1__`): an existing database never runs it (the baseline records it; without that row validate reports it as ignored), a fresh one runs it between `V3` and `V4`.
- Versions compare per dot-separated part as integers, so `V3` == `V3.0`; split versions start at `.1` (`V3.1`, `V3.2`), never `.0`.
- `ignoreMigrationPatterns=*:missing` is the lenient switch for archived originals; without it or `repair`, every existing database fails validation after the move. Kept files still need `repair` for their checksums.
- Repeatables re-run on every checksum change, in alphabetical order, after the versioned files; a repeatable that depends on another must sort after it (`R__010_view_a.sql`, `R__020_view_b.sql`).
- The script column stores the file name only, not the path, so moving a file between locations is invisible; renaming it changes `description` and `script` and `repair` rewrites them.
- Flyway 10 moved database support into plugins (`flyway-database-postgresql`, `flyway-mysql`, `flyway-sqlserver`, `flyway-database-oracle`); a consolidated project still needs the same plugin dependency. Flyway 11 requires Java 17.
- `-- flyway:executeInTransaction=false` on the first line opts a script out of its transaction (needed for `CREATE INDEX CONCURRENTLY`, `CREATE DATABASE`); MySQL has no transactional DDL anyway, so a failed file there leaves partial objects and a `success = false` row that `repair` removes.
- Spring Boot: `spring.flyway.enabled=true`, `locations=classpath:db/migration`, `baseline-on-migrate=false`, `baseline-version=1`, `validate-on-migrate=true`, `out-of-order=false`, `ignore-migration-patterns=*:future`, `table=flyway_schema_history` are the defaults (verified in `FlywayProperties`).
