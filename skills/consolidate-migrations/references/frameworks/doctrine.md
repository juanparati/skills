# Doctrine Migrations 3 (Symfony)

## Layout and naming

- Default directory `migrations/` at the project root, mapped to the namespace `DoctrineMigrations` in `config/packages/doctrine_migrations.yaml` (`migrations_paths: { 'DoctrineMigrations': '%kernel.project_dir%/migrations' }`). Several namespace->directory pairs are allowed.
- File `VersionYYYYMMDDHHMMSS.php` holding `final class VersionYYYYMMDDHHMMSS extends AbstractMigration`. The finder loads every `.php` file in the directory and keeps every declared class in the namespace, so the `Version` prefix is not enforced by code, but the generator uses it and ordering depends on it (below). Keep it.
- The version string is the fully qualified class name (`DoctrineMigrations\Version20240601120000`); that is what the tracking table stores and what the `version` command takes.
- Kept files keep the original's file name **and** class name (`Version20230110100000.php` / `final class Version20230110100000`): the FQCN is the tracking key. Only the body changes, and `getDescription()`, which can name what the file now holds (`'Consolidated: users'`); Doctrine has no way to put the table name in the file name without breaking the class convention, so the description carries it.
- New files (`deferred_foreign_keys`, `seed_reference_data`, `functions_and_triggers`, moved views, split-out tables) are `Version<ts>.php` after the last original, class `Version<ts>` (the plan's `class`).
- The first `Version*` generated by `diff` often creates many tables: the user decides keep together (that class holds the final schema of all of them) or split (the first table created keeps the class; each other one gets `Version<ts+1s>` right after it when that second is free and sorts before the next original, else a file after the last original).

## Replay order

Alphabetical comparison of the version strings (the default comparator does a string compare of the FQCN; the Symfony bundle registers the same). With one namespace and `Version` + 14 digits that is timestamp order. Transcribe originals in that order. Kept classes keep their place; `plan_order.py` numbers new files after the last original.

## Reading originals into ops

Migrations are raw SQL per dialect (`addSql()`), usually generated by `doctrine:migrations:diff`, so reading is SQL parsing in the project's dialect. Things to notice:

- `$this->addSql('CREATE TABLE users (id INT AUTO_INCREMENT NOT NULL, email VARCHAR(180) NOT NULL, UNIQUE INDEX UNIQ_1483A5E9E7927C74 (email), PRIMARY KEY(id)) DEFAULT CHARACTER SET utf8mb4 COLLATE `utf8mb4_unicode_ci` ENGINE = InnoDB')` -> `create_table` with `auto_increment: true` on `id`, an Index `{name: "UNIQ_1483A5E9E7927C74", unique: true}` and `options: {engine, charset, collation}`. The hashed names (`UNIQ_`, `IDX_`, `FK_` + crc) come from Doctrine's naming; keep them verbatim or the next `diff` will rename them.
- Postgres originals create the sequence separately: `CREATE SEQUENCE users_id_seq INCREMENT BY 1 MINVALUE 1 START 1` then `CREATE TABLE users (id INT NOT NULL, ...)` -> `create_sequence` + `create_table`; the column is not `auto_increment` on Postgres (the ORM uses the sequence), transcribe both.
- `ALTER TABLE orders ADD CONSTRAINT FK_E52FFDEEA76ED395 FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE` -> `add_foreign_key`; `diff` emits these after all `CREATE TABLE`s of the same migration.
- `COMMENT ON COLUMN users.roles IS '(DC2Type:json)'` / `'(DC2Type:datetime_immutable)'` -> `set_comment` with the text as-is. These DC2Type comments are how Doctrine remembers the mapped type; dropping them makes `diff` regenerate them.
- `DROP INDEX IDX_x ON orders; CREATE INDEX IDX_y ON orders (user_id, status)` -> `drop_index` + `add_index`.
- `$this->abortIf($this->connection->getDatabasePlatform() instanceof ...)` is the platform guard from `check_database_platform`; it is not an op. `$this->addSql('INSERT INTO ...')` -> `data` op.

## Writing a consolidated table migration

`migrations/Version20230215093000.php`, the kept original that created `orders` (MySQL shown):

```php
<?php

declare(strict_types=1);

namespace DoctrineMigrations;

use Doctrine\DBAL\Schema\Schema;
use Doctrine\Migrations\AbstractMigration;

/**
 * Consolidated: final orders table (created here); folded: Version20230305100100,
 * Version20230801100000, Version20231120100000
 */
final class Version20230215093000 extends AbstractMigration
{
    public function getDescription(): string
    {
        return 'Consolidated: orders';
    }

    public function up(Schema $schema): void
    {
        $this->addSql(<<<'SQL'
            CREATE TABLE orders (
                id INT AUTO_INCREMENT NOT NULL,
                user_id INT NOT NULL,
                number VARCHAR(32) NOT NULL,
                status VARCHAR(16) DEFAULT 'draft' NOT NULL,
                total NUMERIC(12, 2) DEFAULT '0.00' NOT NULL,
                notes LONGTEXT DEFAULT NULL,
                created_at DATETIME NOT NULL COMMENT '(DC2Type:datetime_immutable)',
                UNIQUE INDEX UNIQ_E52FFDEE96901F54 (number),
                INDEX IDX_E52FFDEEA76ED3957B00651C (user_id, status),
                PRIMARY KEY(id)
            ) DEFAULT CHARACTER SET utf8mb4 COLLATE `utf8mb4_unicode_ci` ENGINE = InnoDB
            SQL);
        $this->addSql('ALTER TABLE orders ADD CONSTRAINT CK_orders_total CHECK (total >= 0)');
        $this->addSql('ALTER TABLE orders ADD CONSTRAINT FK_E52FFDEEA76ED395 FOREIGN KEY (user_id) REFERENCES users (id) ON DELETE CASCADE');
        $this->addSql("ALTER TABLE orders COMMENT = 'Customer orders'");
    }

    public function down(Schema $schema): void
    {
        $this->addSql('ALTER TABLE orders DROP FOREIGN KEY FK_E52FFDEEA76ED395');
        $this->addSql('DROP TABLE orders');
    }
}
```

The FK to `users` is inline because `users` is created by an earlier class; otherwise it goes to `deferred_foreign_keys`. A renamed table keeps its creating class; name the former table in the docblock. On Postgres write `CREATE SEQUENCE orders_id_seq INCREMENT BY 1 MINVALUE 1 START 1` first, `id INT NOT NULL`, `COMMENT ON COLUMN / COMMENT ON TABLE` statements, and a down of `DROP TABLE orders` + `DROP SEQUENCE orders_id_seq`. Keep the platform guard (`$this->abortIf(!$this->connection->getDatabasePlatform() instanceof \Doctrine\DBAL\Platforms\MySQLPlatform, ...)`) only if the originals had it.

## Writing a view migration

Same class shape, in the kept class that created the view (or a new `Version<ts>.php` after the last original when even the original holding its final definition comes too early); `addSql()` is the only tool, there is no view DSL:

```php
    public function up(Schema $schema): void
    {
        $this->addSql('CREATE VIEW customer_summary AS SELECT u.id AS user_id, COUNT(o.id) AS order_count FROM users u LEFT JOIN orders o ON o.user_id = u.id GROUP BY u.id');
    }

    public function down(Schema $schema): void
    {
        $this->addSql('DROP VIEW customer_summary');
    }
```

Views are invisible to the ORM, so `doctrine:schema:validate` and `diff` ignore them; a `schema_filter` is not needed.

## The extra files

Each is one more `Version<ts>.php` after the last original, in plan order, only when the plan lists it:

- `functions_and_triggers`: only what no original can hold (it reads something created after every candidate); `addSql()` with the full `CREATE FUNCTION ... $$ LANGUAGE plpgsql` and `CREATE TRIGGER`. Dollar-quoted bodies are fine inside a PHP nowdoc.
- `deferred_foreign_keys`: `$this->addSql('ALTER TABLE users ADD CONSTRAINT FK_1483A5E9F7E2D1E1 FOREIGN KEY (current_team_id) REFERENCES teams (id) ON DELETE SET NULL')`, down drops it.
- `seed_reference_data`: `$this->addSql("INSERT INTO countries (id, name) VALUES (1, 'US'), (2, 'CA')")`, down deletes by key. Data from fixtures (`doctrine/doctrine-fixtures-bundle`) is not a migration; leave it there.

Prerequisites get no file of their own: `CREATE EXTENSION IF NOT EXISTS citext`, `CREATE SCHEMA billing`, `CREATE TYPE invoice_status AS ENUM (...)` and the Postgres `CREATE SEQUENCE ..._id_seq` stay in the kept class that created them, or move into an earlier kept class that needs them.

## Schema snapshot to cross-check

No generated schema file, but the ORM mapping (`#[ORM\Entity]` classes under `src/Entity/`, or XML/YAML mapping) is the source of truth that `diff` compares against. Cross-check the manifest statically: every `#[ORM\Table(name:)]` / class name snake-cased must be a manifest table; `#[ORM\Column(length: 180, nullable: true, options: ['default' => ...])]` must match the column; `#[ORM\JoinColumn(onDelete: 'CASCADE')]` must match the FK; `#[ORM\UniqueConstraint]` / `#[ORM\Index]` must match indexes. `ManyToMany` without `mappedBy` creates an implicit join table named `<owner>_<target>` with two FKs `ON DELETE CASCADE`; it must exist in the manifest even though no entity class names it. The real check after placing the files is `doctrine:migrations:diff` producing an empty migration (needs a database, so it is the user's step).

## After placing the files

- The archive directory must be outside `migrations_paths` **and** outside any autoload path (e.g. `migrations_archive/` at the root, not `migrations/_archive/`): every kept file declares the same FQCN as its archived original (`DoctrineMigrations\Version20230215093000`), the finder is recursive and loads every `.php` it sees, and two classes with the same FQCN is a fatal error (`Cannot declare class ..., because the name is already in use`). Check `composer.json` too: a classmap or PSR-4 entry covering the archive makes `composer dump-autoload` warn about ambiguous class resolution.
- Nothing to regenerate; there is no snapshot. Run `composer dump-autoload` only if the project autoloads `DoctrineMigrations\` via composer (the bundle `require_once`s files itself, so usually not).
- User sanity check: `bin/console doctrine:migrations:status` (lists available vs executed), `doctrine:migrations:diff` (should say "No changes detected"), `doctrine:schema:validate` (mapping vs database; `--skip-sync` to check only the mapping).

## Tracking table and reconciliation

- Table `doctrine_migration_versions` (configurable `storage.table_storage.table_name`), columns `version VARCHAR(191) PRIMARY KEY` (the bundle's default config sets length 192), `executed_at DATETIME NULL`, `execution_time INT NULL` (milliseconds). `version` holds the FQCN. No checksum.
- Applied row with no class on disk: **lenient with a prompt**. `migrate` prints `You have N previously executed migrations in the database that are not registered migrations.`, lists them and asks `Are you sure you wish to continue?` (`--no-interaction` answers yes). `status` shows them as "executed unavailable". A class without a row is pending and runs on the next `migrate`.
- Kept classes already have their row; removed originals still have theirs; new classes have none. Baseline an existing database with `precheck.sql` first (must return no rows: any row is an original that database has not run, and it must be migrated on the old history before anything else):

```sql
SELECT m.v AS not_applied FROM (SELECT 'Version20230110100000' AS v UNION ALL SELECT 'Version20230215093000' AS v UNION ALL ...) m
WHERE NOT EXISTS (SELECT 1 FROM doctrine_migration_versions t WHERE t.version LIKE CONCAT('%', m.v));   -- Postgres: '%' || m.v
```

then `baseline.sh`, which lets the tool rewrite the table from the classes on disk (after the swap, in sibling mode):

```
php bin/console doctrine:migrations:version --delete --all --no-interaction   # deletes every executed row: removed and kept originals
php bin/console doctrine:migrations:version --add --all --no-interaction      # inserts a row per class now on disk: kept and new
php bin/console doctrine:migrations:status
```

(`--delete --all` walks the *executed* list, `--add --all` the *available* list, verified in `VersionCommand`.) Net effect: removed rows gone, kept rows back (with a new `executed_at`), new rows added. When the console cannot be run against that database, the equivalent SQL by hand (`baseline.py` writes only the commands) touches only removed and new classes:

```sql
DELETE FROM doctrine_migration_versions WHERE version IN ('DoctrineMigrations\\Version20230305100100', 'DoctrineMigrations\\Version20230801100000', ...);  -- removed originals only
INSERT INTO doctrine_migration_versions (version, executed_at, execution_time)
VALUES ('DoctrineMigrations\\Version20231120100001', NOW(), 0);  -- one per new class
```

Never delete by prefix (`LIKE 'DoctrineMigrations\\Version2023%'`): that takes the kept rows too, and the kept classes would run again. `\\` is MySQL's escaped backslash; on Postgres write a single `\`.

Alternative built into the tool: `doctrine:migrations:rollup` deletes all tracked versions and inserts the one version on disk, but it refuses with more than one available migration, so it only fits a single-file consolidation (`doctrine:migrations:dump-schema` + `rollup` is Doctrine's own squash).

## Quirks

- Class names: any class in the file is registered, so a helper class in the migrations directory becomes a "migration" and breaks `migrate`. One class per file, `Version` + 14 digits, namespace `DoctrineMigrations`. A kept class keeps its exact name and namespace; renumbering it makes it a new, unapplied migration.
- A database that ran `Version20230215093000` but not yet `Version20230305100100` sees the rewritten class as executed and never gets the folded column; nothing fails. The precheck catches it.
- Ordering is a string compare of the FQCN, not a numeric one: mixing namespaces or a shorter digit count changes the order.
- The `version` argument of `doctrine:migrations:version` is the FQCN; quote the backslashes (`'DoctrineMigrations\Version2024...'`).
- `transactional: true` (default) wraps each migration in a transaction; MySQL DDL commits implicitly, so a failed consolidated file leaves a half-created table. Postgres rolls DDL back. `all_or_nothing` (default false) wraps the whole `migrate` run.
- DC2Type column comments are part of the schema for `diff`; omit `COMMENT '(DC2Type:json)'` and the next diff re-adds it.
- `doctrine:migrations:diff` and `schema:validate` need a live database; the skill's static check only compares the manifest with the mapping.
- Doctrine-generated constraint names are hashes of table and column names (`FK_` + crc32 of table + crc32 of columns); keep them so later `diff` output stays stable.
