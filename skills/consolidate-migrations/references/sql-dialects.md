# DDL cheat-sheet for raw-SQL migration tools

For Goose, Atlas, Diesel, SQLx, Flyway, Prisma, Doctrine (`addSql`), TypeORM (`queryRunner.query`), Liquibase formatted SQL, and any DSL's `execute`/`DB::statement` escape hatch. Keep the dialect of the originals: a consolidated file must run where the originals ran. When the manifest's `dialect` is unknown, ask.

## Create table

**Postgres**

```sql
CREATE TABLE billing.invoices (
    id            bigserial PRIMARY KEY,                          -- or: bigint GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
    customer_id   bigint NOT NULL REFERENCES customers (id) ON DELETE RESTRICT,
    status        invoice_status NOT NULL DEFAULT 'draft',
    amount_cents  bigint NOT NULL DEFAULT 0,
    currency      char(3) NOT NULL DEFAULT 'EUR',
    created_at    timestamptz NOT NULL DEFAULT now(),
    CONSTRAINT invoices_amount_cents_nonnegative CHECK (amount_cents >= 0)
);
CREATE INDEX invoices_customer_id_idx ON billing.invoices (customer_id);
COMMENT ON COLUMN billing.invoices.currency IS 'ISO 4217';
```

Named FK: `CONSTRAINT invoices_customer_id_fkey FOREIGN KEY (customer_id) REFERENCES customers (id) ON DELETE RESTRICT`. Keep the original's names when it had them; Postgres's default names are `<table>_<col>_fkey`, `<table>_<col>_key` (unique), `<table>_pkey`.

**MySQL / MariaDB**

```sql
CREATE TABLE invoices (
    id            bigint unsigned NOT NULL AUTO_INCREMENT PRIMARY KEY,
    customer_id   bigint unsigned NOT NULL,
    status        enum('draft','paid','void') NOT NULL DEFAULT 'draft',
    amount_cents  bigint NOT NULL DEFAULT 0,
    created_at    timestamp NULL DEFAULT CURRENT_TIMESTAMP,
    UNIQUE KEY invoices_number_unique (number),
    KEY invoices_customer_id_index (customer_id),
    CONSTRAINT invoices_customer_id_foreign FOREIGN KEY (customer_id) REFERENCES customers (id) ON DELETE RESTRICT,
    CONSTRAINT invoices_amount_cents_nonnegative CHECK (amount_cents >= 0)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci COMMENT='...';
```

A referencing column needs an index; MySQL creates one implicitly for an FK, but declare it when the originals did so names stay stable. Column comments go inline: `name varchar(255) NOT NULL COMMENT 'Display name'`.

**SQLite**

```sql
CREATE TABLE "Post" (
    "id"        INTEGER NOT NULL PRIMARY KEY AUTOINCREMENT,
    "title"     TEXT NOT NULL,
    "published" BOOLEAN NOT NULL DEFAULT false,
    "authorId"  INTEGER NOT NULL,
    "createdAt" DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    CONSTRAINT "Post_authorId_fkey" FOREIGN KEY ("authorId") REFERENCES "User" ("id") ON DELETE CASCADE ON UPDATE CASCADE
);
CREATE INDEX "Post_authorId_idx" ON "Post"("authorId");
CREATE UNIQUE INDEX "User_email_key" ON "User"("email");
```

SQLite cannot `ALTER TABLE ... ADD CONSTRAINT`, `DROP COLUMN` with constraints, or change a column type: that is why histories on SQLite contain table-rebuild blocks. In a consolidated file none of that is needed: each table is created once, complete. FK targets are not validated at CREATE time, so cycles and FKs to tables created in a later file stay inline. Checks are inline `CHECK (...)` only.

**SQL Server**

```sql
CREATE TABLE dbo.Invoices (
    Id          bigint IDENTITY(1,1) NOT NULL CONSTRAINT PK_Invoices PRIMARY KEY,
    CustomerId  bigint NOT NULL CONSTRAINT FK_Invoices_Customers REFERENCES dbo.Customers (Id) ON DELETE NO ACTION,
    Status      nvarchar(20) NOT NULL CONSTRAINT DF_Invoices_Status DEFAULT 'draft',
    CreatedAt   datetime2 NOT NULL CONSTRAINT DF_Invoices_CreatedAt DEFAULT SYSUTCDATETIME()
);
CREATE INDEX IX_Invoices_CustomerId ON dbo.Invoices (CustomerId);
```

Defaults are named constraints; keep the names from the originals (EF Core generates `PK_`, `FK_`, `IX_` names).

## Deferred foreign keys (the `deferred_foreign_keys` file)

```sql
-- postgres / mysql / mssql
ALTER TABLE users ADD CONSTRAINT users_current_team_id_foreign
    FOREIGN KEY (current_team_id) REFERENCES teams (id) ON DELETE SET NULL;
-- down
ALTER TABLE users DROP CONSTRAINT users_current_team_id_foreign;     -- mysql: DROP FOREIGN KEY users_current_team_id_foreign
```

## Prerequisites (schemas, extensions, types, sequences, functions)

They are written in the kept original that created them (`00001_extensions_and_schema.sql` keeps the schema and the extension, `00003_create_invoice_status_type.sql` the type), or in an earlier kept file when the plan moved them there; the plan lists them per file under `prerequisites`. Shown together here:

```sql
CREATE SCHEMA IF NOT EXISTS billing;
CREATE EXTENSION IF NOT EXISTS citext;
CREATE TYPE invoice_status AS ENUM ('draft', 'paid', 'void');       -- all final values at once; no ALTER TYPE ... ADD VALUE needed
CREATE SEQUENCE invoice_number_seq START 1000;
CREATE OR REPLACE FUNCTION set_updated_at() RETURNS trigger LANGUAGE plpgsql AS $$
BEGIN NEW.updated_at = now(); RETURN NEW; END $$;
-- down, in reverse order
DROP FUNCTION IF EXISTS set_updated_at();
DROP SEQUENCE IF EXISTS invoice_number_seq;
DROP TYPE IF EXISTS invoice_status;
DROP EXTENSION IF EXISTS citext;
DROP SCHEMA IF EXISTS billing;
```

MySQL has no standalone enum types (they are inline column types), no extensions, no schemas in the Postgres sense (a MySQL "schema" is a database). Functions and triggers exist (`DELIMITER` is a client feature: in migration files write the body without it, Goose needs `StatementBegin/End`, Flyway handles `$$`-less bodies natively).

Values that were added with `ALTER TYPE ... ADD VALUE` over time are already merged in the manifest; write the type once with all values. Goose files that contained `ADD VALUE` needed `-- +goose NO TRANSACTION`; a single `CREATE TYPE` does not.

## Triggers

In the file the plan lists them under (`triggers`): the original that created the trigger, usually the table's own file or the one that created the trigger function (`00007_updated_at_trigger.sql` holds the function and its trigger):

```sql
CREATE TRIGGER invoices_set_updated_at BEFORE UPDATE ON billing.invoices
    FOR EACH ROW EXECUTE FUNCTION set_updated_at();
-- down
DROP TRIGGER IF EXISTS invoices_set_updated_at ON billing.invoices;
```

## Views

```sql
CREATE VIEW customer_summary AS
SELECT c.id AS customer_id, c.email, count(i.id) AS invoice_count
FROM customers c LEFT JOIN billing.invoices i ON i.customer_id = c.id
GROUP BY c.id, c.email;
-- materialized (postgres)
CREATE MATERIALIZED VIEW billing.monthly_revenue AS SELECT ...;
CREATE UNIQUE INDEX monthly_revenue_month_idx ON billing.monthly_revenue (month);
-- down
DROP MATERIALIZED VIEW IF EXISTS billing.monthly_revenue;
DROP VIEW IF EXISTS customer_summary;
```

Keep the SELECT verbatim from the last definition in the history. Column names referenced inside it must be the **final** names (a view written before a column rename was invalidated by that rename in Postgres, or silently rewritten; the manifest holds the final names, so check the SELECT against them).

## Seeds (the `seed_reference_data` file)

Idempotent forms, so running the file twice is harmless:

```sql
INSERT INTO roles (name) VALUES ('admin'), ('member') ON CONFLICT (name) DO NOTHING;   -- postgres, sqlite
INSERT IGNORE INTO roles (name) VALUES ('admin'), ('member');                           -- mysql
IF NOT EXISTS (SELECT 1 FROM roles WHERE name = 'admin') INSERT INTO roles (name) VALUES ('admin');  -- mssql
```

Down: `DELETE FROM roles WHERE name IN ('admin', 'member');`

## Quoting and case

Follow the originals. Prisma and EF Core quote every identifier and use camel/Pascal case; Rails, Laravel, Django and most hand-written SQL use unquoted snake_case. Mixing styles in one database works but reads badly, and on Postgres a quoted mixed-case name is a different name from the unquoted one.
